## Part 1 — Border width as a first-class token

Today border thickness is not a variable: the spec's token-only lint whitelists a hardcoded 1px border width as a structural constant, color tokens (`--border`, `--input`) are the only border tokens, and manifest border knobs (e.g. Dialog's) only toggle presence (`none` / `border`). Make thickness an identity-level dimension, following the exact pattern `--radius` already uses.

1. **Token contract (append-only addition).** Add a dimension token `--border-width` to the contract and to the theme item emission, alongside `--radius`. It is mode-independent (same value light/dark). Arche Default and the aurora identity carry `1px` — existing identities must render pixel-identically after this change.
2. **Legal values + profiles.** Legal set: `0px, 1px, 2px, 3px`. Per-profile bounds for *generated* payloads, recorded as an enforce-tier rule in `design-rules.json` (new rule id `border-width-profile-bounds`): enterprise {0, 1}, standard {0, 1, 2}, expressive {0, 1, 2, 3}. Hand-authored payloads: any legal-set value validates; out-of-set values fail like any contract violation.
3. **Templates.** Replace the hardcoded 1px border width in component templates with the token (Tailwind v4 length-variable syntax or an emitted utility — choose the mechanism that keeps templates token-only). Update the lint whitelist: the 1px border-width exception is removed; border widths in templates must come from the token. Presence knobs keep their meaning: `none` renders no border regardless of the width token. Focus ring width is **not** part of this change (ring tokens/behavior unchanged).
4. **Compiler / DNA mapping (deterministic table, compilerVersion bump).** Default `1px`. Map upward only on strong signals: sharpness ≥ 0.8, **or** retroFuturism ≥ 0.7 combined with playfulness ≥ 0.5, **or** material `pixel` → `2px` (standard profile) / up to `3px` (expressive profile); formality ≥ 0.8 forces `1px`. Enterprise profile caps at `1px` regardless of axes. Record the selection like any compiled value; manual payload edits to the token are ordinary overrides.
5. **Spec note.** Append a dated amendment note to the Library Creation Spec recording: the contract addition (append-only), the lint-whitelist removal, and the profile bounds — so the spec and the code don't drift. Do not rewrite other spec sections.
6. **Emitter + previews.** Re-emit the canonical identities; Brief #1/#2-style scratch previews must show Arche Default unchanged (1px everywhere) and a test fixture at `2px` visibly thicker across Button, Card, Dialog, Input, Table.

It complements — never replaces — the Acme Tasks hero demo, which stays exactly as it is.

1. **Manifest-driven, never hand-listed.** A shared `KitchenSink` component (in `apps/web`, reusable by preview contexts) reads the foundation catalog + manifests and renders one section per manifest category (actions, forms, overlays, navigation, feedback, layout, data), one block per component. Adding a component to the catalog must add it to the sink with no sink code changes. Expected inventory cross-check (37): Button, Toggle, Toggle Group, Toolbar · Label, Input, Textarea, Checkbox, Radio Group, Select, Slider, Switch, Form, One-Time Password Field, Password Toggle Field · Dialog, Alert Dialog, Popover, Hover Card, Context Menu, Dropdown Menu, Tooltip · Menubar, Navigation Menu, Tabs · Progress, Skeleton, Toast · Accordion, Collapsible, Card, Separator, Aspect Ratio, Scroll Area · Table, Avatar, Badge.

3. **Reuse the docs examples.** Where Brief #3's manifest-generated component pages already define example compositions, the sink imports those same example definitions — one source of examples for docs and sink, never a second hand-written copy.
4. **Foundation strip first.** Above the component sections: the active identity's foundation on one screen — all contract color tokens as labeled swatches, the type-scale steps rendered as real text, radius steps, the `--border-width` value rendered as sample bordered boxes, and the chart palette. This strip is the fastest single-glance identity check.
5. **Realistic Acme content.** Sample content is coherent Acme Inc. material (task names, people, orders, numbers) consistent with the Acme Tasks demo's world — no lorem ipsum, no "Component 1" filler. Interactive pieces actually work (tabs switch, accordion opens, slider slides, table sorts if the template supports it).

Light/dark toggle applies to the whole page. A slim sticky section nav (category anchors + component index) runs alongside — this page is long by design.

## Part 3 — Landing page + dashboard polish pass

A refinement pass over the existing public site (landing, Examples, Docs, Pricing, sign-in) and dashboard (home, library detail, component browser, Studio, Settings). "A design team shipped this" is the bar. This is **not** a redesign or a feature project.

**Hard constraints**

- No structural changes: routes, IA, section order, features, and functionality stay as-is — **except** the specific additions named in Part 4, which are authorized. Any other structural idea goes in the final report as a recommendation, not code.
- Theming law: colors from the Arche identity tokens only, never hardcoded; the identity litmus test (edit token → republish → site re-skins, no code change) must still pass, now including `--border-width`.
- Copy discipline: no invented facts — no customer counts, testimonials, logos, or "trusted by" claims. Existing copy/pricing content stays unless factually wrong about the shipped product; flag those in the report. Buttons say the real action.
- Dark mode parity on every fix. The rotating Acme Tasks demo stays as-is conceptually; polish presentation only.

**Method**

1. Audit first, in writing: every surface at desktop + mobile, light + dark, issues grouped by surface and tagged by the categories below with severity (distracting / noticeable / subtle). Use the Part 2 kitchen sink as the component-level audit surface — inconsistencies between how a component looks in the sink vs. in situ are audit items.
2. Fix surface by surface, landing first, dashboard second, in this priority order within each surface: spacing/layout rhythm → typography hierarchy → alignment consistency → color/token discipline → interactive states → motion → responsive edges.
3. Final report: audit list with dispositions (fixed / not fixed + why), files changed grouped by surface, recommendations separated as not-done.

**What "professional" means here**

- *Spacing & layout:* everything on the 4px/8px grid; consistent section padding rhythm on the landing page; shared container edges; cards in a row share baselines/equal heights where implied; whitespace creates grouping before boxes and borders do.
- *Typography:* one type scale across both surfaces (kill near-duplicate sizes); exactly one loudest element per view; hierarchy from size/weight, not color; headline measure < ~80 chars, prose 65–75ch; tabular figures for dashboard numbers; one consistent treatment each for labels, captions, metadata.
- *Color:* aurora gradients are washes behind content only — never text fill, never the first thing noticed; saturated color spent in one place per view; one border/shadow convention applied uniformly (now including consistent border width from the token); every text pairing AA in both modes, muted text checked explicitly.
- *Components & states:* complete states everywhere (hover, focus-visible with a real ring, active, disabled) with no layout shift between states; one primary/secondary/ghost button treatment across landing and dashboard; Lucide only, one icon size scale and stroke weight; radius by role consistently, nested surfaces follow outer = inner + gap.
- *Landing:* hero = headline + subhead + one primary CTA + the demo, nothing competing; sections alternate visual weight instead of an unbroken stack of identical card grids; pricing's recommended plan distinguished by one strong cue; footer complete and grid-aligned.
- *Dashboard:* calm density — consistent row heights, table header treatment, numbers right-aligned where compared; sidebar quieter than content, one clear active-nav cue; Quick Install's command is its panel's hero (monospace, copy with copied feedback); Recent Activity reads as a timeline; library items share identical structure and one small semantic badge set; **every list/table/panel has designed loading (layout-matching skeletons), empty (what it is + the one action that fills it), and error states** — no blank voids, no spinner-only content areas; in the Studio, the preview (now the kitchen sink) is the visual center and the chrome never out-shouts it.
- *Motion:* restrained — 150–250ms on existing easing tokens, at most one orchestrated moment per view, no fade-up-on-every-block or hover-lift-on-every-card defaults, `prefers-reduced-motion` respected throughout.
- *Responsive:* verify 360 / 768 / 1024 / 1440 on every surface — no horizontal scroll, overlap, or clipped text; tap targets ≥ 44px on touch layouts; tables degrade by existing patterns only.

**Anti-patterns to hunt and remove:** uniform radius + uniform soft shadow on every card; nested cards; ALL-CAPS eyebrow labels over every heading; gradient headline text; purple-blue glow accents; grids of identical feature cards as the only section form; fake social proof; centered-everything layouts; scroll-triggered fade-ups everywhere; mixed icon styles; mixed warm/cool grays.

## Part 5 — Aliveness inside the product

The same machinery becomes product behavior, so what users publish carries it too. Three integrations, in scope order:

1. **Publish-time specimen assets.** Extend the publish pipeline: on every successful publish, render the identity's kitchen sink (light + dark) and foundation strip through the existing screenshot/render path and store the captures as versioned assets alongside the snapshot. Generate from them: (a) the public identity page's hero specimen, (b) an Open Graph / social share image for the identity's public link (identity name, prompt, sink specimen, Arche mark — composed from real renders), (c) the gallery/latest card thumbnail used in Part 4.4. Assets are immutable per version, like the snapshot itself; republishing creates new assets, never overwrites. If headless rendering is unavailable in the environment, implement the capture via the existing preview-app route and report the mechanism used.
2. **Presentation guidance through MCP + Standards.** Identities should teach consuming agents how to *present* them, not just their values. (a) The hosted MCP `get_identity` response gains a `presentation` block generated from the payload + design rules: imagery treatment (the identity's texture/material expressed as guidance, e.g. "flat color fields, no photography treatment" vs. "grain overlay at low opacity"), motion choreography (the motionFeel translated into concrete guidance: durations/easing from the tokens, one orchestrated moment per view, reduced-motion rule), specimen usage (links to the Part 5.1 assets), and the anti-slop calibration items relevant to this identity's profile. All generated deterministically from existing data — no new model calls. (b) Add the corresponding Standards entries (presentation category) to the relevant manifests where a component's presentation is rule-bound (e.g. Toast choreography, Dialog entrance) — ids permanent, enforcement posture unchanged (this does not decide O1).
3. **Freshness as a user-facing product surface.** (a) Every public identity page gains a **version timeline**: version number, date, what changed (from the publish/diff records — DNA deltas and adjustment summaries in plain language), with its specimen assets — an identity's history reads as a story, the way enterprise product pages show evolution. (b) The dashboard library view surfaces the same timeline plus the share assets (copy-link with the OG image preview), so a user publishing an identity gets the "launch kit" automatically: specimen renders, share image, install command, public page.

Explicitly **not** in Part 5: scroll-story/composition generation for users' apps (that is the blocks/templates layer, still an open decision — Part 5 must not preclude it, and the presentation guidance is written so a future composition layer can consume it), video generation for users (the film in Part 4.3 is Arche's own, produced once), and any change to publish gates or entitlement behavior.

## Part 6 — Blocks layer (base)

Add **blocks**: complete, installable page sections composed from Arche components, distributed exactly like components — per-identity registry items that any identity re-skins, installed through the same CLI. This is the base layer only: curated, installable units. AI arranging blocks into full pages (blueprints/generative composition) remains a future layer and is **not** built here.

**Standards adopted, not invented** (fetch and conform; do not design from scratch):
- **Format:** shadcn's official registry standard already defines this — items of type `registry:block` in the registry-item JSON schema (`https://ui.shadcn.com/schema/registry-item.json`), installed by the same `add` flow, with `files[].target` placement placeholders (`@components/`, `@ui/`, `@lib/`, `@hooks/`). Arche block items must validate against that published schema; Arche's emitter extends, never forks, the item format it already emits for components.
- **Taxonomy:** category and naming conventions follow the converged market taxonomy — shadcn's official block categories (dashboard, sidebar, login, signup, charts) and Tailwind Plus's marketing sections (hero, feature, CTA, bento, pricing, header, stats, testimonials, newsletter, blog, contact, team, logo clouds, FAQs, footers, banners, 404) and application patterns (shells, page headings, tables, lists, feeds). Variant naming describes **layout composition** (centered, split, with-media), never style — style is the identity's job.
- **Section discipline:** one job per block (from the landing-page research behind Part 3/4); a page has one h1 — every block manifest declares its heading role; landmark semantics per block type (header/nav/main/footer/aside) are part of the template, not the consumer's problem.
- **Reference implementations (read before authoring):** shadcn's official blocks are open source (MIT) in the shadcn-ui repository's blocks registry — study dashboard-01, the sidebar blocks, and login blocks for composition structure, file organization, and how a block declares its dependencies before writing Arche's app-shell/dashboard-home/auth blocks. Vercel's registry starter shows the same item architecture end-to-end. Tailark's free marketing blocks (shadcn registry format) are the reference for marketing-section composition. These are **structural** references: composition, file layout, dependency declaration. Never copy their styling, class recipes, or content — Arche blocks compose Arche catalog components with Arche tokens only, and must pass Arche's token-only lint and manifest agreement checks, which the references would fail.

**Block manifest** = the component manifest schema, plus a `composition` section:
- `contentSlots`: typed slots with cardinality — e.g. hero: `eyebrow?` (short text), `headline` (text), `subhead?`, `cta` (max 2 actions, exactly ≤1 primary), `media?` (image/component region). No untyped free-form children where a typed slot exists.
- `childComponents`: catalog components the block composes, with min/max counts where meaningful. Blocks compose **only** catalog components + contract tokens — no new primitives, no raw values (token-only lint applies unchanged).
- `layoutAxes`: block-level variant axes in the same cva style as components (e.g. hero `alignment: center | left`, `media: none | right | below`; features `layout: grid | bento | split`).
- `standards`: useWhen / doNotUseWhen + block rules with permanent ids (e.g. `hero-one-primary-cta`, `pricing-max-four-tiers`, `testimonials-no-fabricated-quotes` — content slots for testimonials require a named source field, and Arche's own site rules from Part 3 apply to Arche's usage).

**v1 catalog — 20 blocks** (one template each; breadth via layout axes, not variant sprawl):
- *Marketing (11):* site-header, hero, logo-cloud, features, stats-band, testimonials, pricing, faq, cta, newsletter-signup, site-footer.
- **site-header is the navbar.** There is deliberately no Navbar in the component catalog (Radix has no such primitive; Navigation Menu and Menubar are the catalog's navigation components). site-header composes them — logo slot, Navigation Menu link row, action buttons, optional avatar Dropdown Menu, and a mobile collapse pattern — into the one navbar users install. Do not add a Navbar component to the catalog, and do not let block consumers hand-compose headers when this block exists; its manifest's `childComponents` and standards (one header per page, landmark `banner` role, mobile menu focus behavior) carry the rules.
- *Application (9):* app-shell (sidebar layout), dashboard-home (KPI row + chart region + activity feed composed), stats-row, data-table-page (toolbar + table + pagination + empty state), settings-page, activity-feed, empty-state, auth-login, auth-signup.
Each block ships with realistic Acme sample content as its default slot fill (replaceable, typed), consistent with the demo/sink world.

**Pipeline integration (same as components, everywhere):**
- Foundation: blocks live beside components (`packages/foundation/blocks/` — template + manifest per block); the manifest↔template cross-check extends to blocks; the catalog count becomes components + blocks and is reported as such.
- Emitter: registry-core emits one `registry:block` item per block per identity, `registryDependencies` naming the component items it composes; blocks appear in the library's item listing and install via the existing `arche add <block>` / stock shadcn path with no CLI changes beyond listing (verify; if `arche list` filters by type, extend it).
- Publish gate: blocks validate like components (manifest agreement, token discipline, AA under the publishing identity — a block that fails contrast under an identity fails that identity's publish, same as components).
- MCP: catalog tools gain blocks — `list_blocks` (optional category) and `get_block` mirroring the component tools, from the same tool registry; `check_placement` evaluates block standards too (e.g. two heroes on one page → violation of the one-h1/heading-role rule when page context is supplied).
- Docs/gallery: blocks get manifest-generated pages like components (live full-width preview under the active identity, slot table, layout axes, install command); the public Examples surface gains a Blocks view. The kitchen sink stays components-only.
- Design rules: teach-tier gains the block discipline (one job per section, heading roles, slot respect); Shapeshift does **not** generate blocks in this part — blocks are hand-authored Arche assets that identities skin, exactly like component templates.

## Part 7 — Full-page preview with floating edit + identity swap

A try-it-live surface: complete, realistic full pages composed **entirely from Part 6 blocks** (plus catalog components inside them), rendered under a chosen identity at full viewport, with floating controls to swap identities in place and jump into editing. This is the product's "walk through the house" moment — distinct from the hero's Acme Tasks rotation (marketing) and the kitchen sink (component QA); it replaces neither.

1. **Two reference pages**, both fixed compositions of Part 6 blocks with the standard Acme sample content:
   - *Site page:* site-header → hero → logo-cloud → features → stats-band → testimonials → pricing → faq → cta → newsletter-signup → site-footer.
   - *App page:* app-shell containing dashboard-home, a data-table-page view, and a settings-page view (switchable via the shell's own navigation).
   No hand-built page furniture outside blocks/components; if a needed pattern is missing, that is a Part 6 gap — report it, don't improvise a one-off.
2. **Route + entry points.** Immersive route in `apps/web` (e.g. `/preview`), chrome-light (no site header/footer around it — the previewed page *is* the page). Entry points: a "Full-page preview" action on Examples, on public identity pages (`/p/...`), in the Studio (previewing the draft being edited), and as the transformation story's final-beat link in Part 4.2. URL carries the identity + page + mode (e.g. `?identity=<user>/<library>&page=site&mode=dark`) so previews are shareable links.
3. **Floating control bar** (fixed, bottom-center on desktop / bottom sheet-safe on mobile, above the previewed content, visually distinct from it — Arche chrome, not preview content): 
   - **Identity switcher:** menu listing identities with color swatches + names — the canonical fixtures, Arche aurora, the signed-in user's own libraries/drafts (when authenticated), and the identity the user arrived from. Selecting one re-skins **both** reference pages instantly: theme recompiled client-side from the payload through the same compilation path as the site theme, **no page reload, no flash of unstyled or previous-identity content**, scroll position and in-page interactive state (open tab, table page) preserved where feasible.
   - **Page toggle:** Site / App.
   - **Mode toggle:** light / dark (defaults to the identity's own default mode behavior, user-overridable).
   - **Viewport toggle:** desktop / mobile width frame (for quick responsive checks) — desktop only control.
   - **Edit button (the floating action):** a clearly primary floating button labeled with a pencil icon + "Edit". It opens the **in-preview editor panel** (item 6 below) for the current identity, without leaving the page. Behavior by ownership: own identity (or own draft, incl. arriving from Studio) → edits land on that draft; someone else's public identity or a fixture → "Remix" semantics: opening the editor creates a draft copy owned by the user (sign-in required; anonymous users get the sign-in flow with return) and all edits land on the copy — the original is never mutated, and the panel header says whose draft is being edited. Label reflects the action ("Edit" vs. "Remix to edit") so the semantics are honest. The panel also carries an "Open in Studio" action for the full editor.
4. **Preview honesty + sandboxing.** Preview content is the fixed Acme sample data; interactive elements genuinely work within the page (menus, tabs, dialogs, table pagination) but mutate nothing real — state is in-memory and resets on identity/page change where state doesn't carry. A small persistent "Preview" badge (part of the floating chrome) makes the sandbox nature unambiguous without covering content.
5. **Performance + correctness constraints.** Identity swap completes as a theme application, not a refetch of the page composition (block tree rendered once per page selection; payloads may be fetched/cached per identity). Every offered identity must render AA-valid (they all passed the publish gate or are fixtures — drafts in Studio context show their current validation state in the switcher if invalid, and still preview, since a draft's job is to be looked at). `prefers-reduced-motion` disables swap transitions. Keyboard: the floating bar is fully reachable and operable, focus never trapped behind preview content, and `Esc` closes the switcher menu returning focus to its trigger.
6. **Real-time manual editing inside the preview.** The editor panel (right-side drawer on desktop, full-screen sheet on mobile; the previewed page stays visible and live beside/behind it) edits the working draft with **every change reflected on the previewed page in real time** — same theme-recompile path as identity swapping, no reload, no Apply button. Contents:
   - *Identity tab:* the draft's tokens in grouped controls (color tokens as OKLCH-aware color fields with the compiled value shown, `--radius`, `--border-width`, motion tokens), font/icon selections (registry pickers), type-scale selection, and — for generated identities — the DNA sliders/enums, which recompile through the style compiler exactly as in the Studio (Brief #6 behavior; manual token edits register as overrides under the existing override rules).
   - *Components tab:* per item 7 — the components present on the current page listed first, then the full catalog; selecting one opens its knob controls with its live preview.
   - *Live validation:* the validator runs on the draft as edits happen; findings appear inline in the panel (rule id + token/component + plain message) and a status chip shows the draft's publish-readiness. Findings never block editing; they block publishing, per the existing gate. Design-rule envelopes apply as findings on manual edits (not silent clamps — the user's hand is visible; generated values remain clamped by the compiler as before).
   - *Persistence:* edits autosave to the draft (debounced; a saved/unsaved indicator in the panel). Publishing is never implicit — it stays the explicit Studio action. Closing the panel or swapping identity keeps draft edits (they belong to the draft, not the preview session); swapping to a *different* identity while edits exist simply switches which draft is shown — each identity's draft state is its own.
7. **Per-component editing with per-component preview — in the preview panel AND the dashboard Studio.** Identity editing is component-granular, specified here for both editors (they share one implementation of the component editor):
   - A user can select **any specific component** (e.g. Button, Dialog, Card) and edit its manifest knob selections for the identity (default variant/size, shadow, overlay opacity, backdrop blur — whatever that component's manifest declares). Controls are generated from the manifest: every control offers exactly the knob's legal values — illegal values are unrepresentable, as in the existing Studio editor.
   - **Every component edit shows that component's live preview while editing:** a preview pane rendering the actual component from the draft identity — all its axis values in a compact variant grid (e.g. Button: every variant × size, incl. disabled), updating in real time as knobs change. In the dashboard Studio this preview pane sits beside the component's controls (extending the existing mini-render cards into the editor itself, per component, not just library-level cards); in the preview panel it appears in the Components tab, with an additional "see it on the page" affordance that scrolls to and highlights the component's instances in the full-page preview when the current page uses it.
   - Token edits show their blast radius: when a token changes, the Components tab marks which components use it (from manifests' `tokensUsed`), so the user can jump to the affected previews.

## Acceptance criteria

1. `--border-width` is in the contract, emitted in the theme item, and present at `1px` in Arche Default + aurora payloads; re-rendered previews of both are pixel-identical to before.
2. A `2px` test fixture shows visibly thicker borders across Button, Card, Dialog, Input, Table in a scratch install; template grep finds no hardcoded border-width values; the lint whitelist no longer contains the 1px exception.
3. `design-rules.json` contains `border-width-profile-bounds`; an expressive generation with high sharpness compiles to 2–3px with the choice recorded; an enterprise generation never exceeds 1px.
4. Spec amendment note exists and matches the implementation.

**Part 2**
5. The sink renders all 37 catalog components; an automated coverage check cross-references manifests and asserts every component block exists and every axis value is rendered at least once (using the `data-*` hooks) — the check fails if a component is removed from the catalog rendering.
